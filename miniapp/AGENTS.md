# 微信小程序开发规则

## 适用范围

本文件适用于 `miniapp/` 及其子目录，补充根目录 `AGENTS.md` 和 `docs/development-workflow.md`。发生冲突时，以资金与设备安全铁律、用户当前明确指令和主工作流验收门为准。

## 当前阶段

小程序页面验收与接真状态以 `docs/demo-module-status.md` 为唯一状态源；所属 B 链与宏观 `E2E-*` 旅程状态以 `docs/requirements/demo-business-chain-matrix.md` 为唯一来源。Demo 页面基线继续保留，但不再把全部小程序任务统一默认为 Demo 定型。每次任务必须先读业务链矩阵、`docs/requirements/decisions.md` 和对应契约，再判断是 Demo 定型、契约待验收、真实实现还是已有模块维护。

属于 Demo 定型的链路执行 D0～D4：业务故事 → 接口契约 → 页面 + Mock → 用户验收。当前小程序已完成 E2E-01 扫码取水、E2E-02 水卡生命周期和 E2E-03 水配送的模拟环境内部验收；后续任务按业务链矩阵中的 E2E-04～E2E-08 状态推进。

用户可以一次授权一个边界明确的纯代码实现包；授权包内的正常编码、本地无副作用测试和文档同步不按人为切片反复停工。主库迁移、任何持久余额/水量变化、Pay-Sim 实际运行、真实支付（含查单/退款）、其他外部调用或设备指令仍须在实际执行前逐次获得用户明确授权，不得由纯代码包的授权隐式扩张。

技术基线固定为：unibest（uni-app + Vue 3 + TypeScript）+ Wot UI。初始化时不得创建独立 Git 仓库，也不得把依赖缓存和构建产物纳入交付包。

## 开发前必读

1. 根目录 `AGENTS.md`、`docs/development-workflow.md` 与 `docs/demo-module-status.md`。
2. 需求基线、对应 REQ ID 和 `docs/requirements/demo-business-chain-matrix.md` 中的业务链状态。
3. `miniapp/README.md` 中已经确认的信息架构、页面职责、状态机和外部边界。
4. `miniapp/.agents/skills/wot-ui/SKILL.md` 全文。
5. 实际使用组件对应的 `miniapp/.agents/skills/wot-ui/references/*.md`。
6. 涉及设备交互时读取 `docs/mqtt-topics.md`，但小程序不得直接连接 MQTT 或代替服务端下发设备指令。

不得凭其他组件库经验猜测 Wot UI 的 props、events、slots、类型或平台兼容性。组件 API 以本地 Skill 参考为准；初始化命令、运行时版本和平台能力以实施时核验的官方资料为准。

## 账号、能力与数据范围

- 同一个 `ws_user/accountId` 是小程序唯一账号主体，不建立用户、机主、配送员三个互斥登录身份。
- 用户能力是登录后的基础能力：扫码取水、充值、订水、订单查询和配送申诉。
- 机主能力来自本人水站/设备授权范围：设备、经营和收益只读视图，以及报修入口；Demo 初期不提供远程设备控制。
- 配送工作能力来自状态为“已启用”的配送员记录：服务范围内可接任务、本人任务、配送、三照与履约状态；申请、待审、停用和驳回不授予工作能力。
- 同一账号不得配送自己的订单。可接任务列表必须排除下单用户等于当前用户的任务，接单接口还必须重复校验；禁止只靠页面过滤。
- 三项能力可以在同一账号同时存在。全应用固定一套 `首页 / 订单 / 我的` Tabbar，首页按 capability registry 分组投影用水、配送和经营入口，不使用全局 `currentRole`、身份选择页或三套“我的”。

前端能力投影只改善导航，不构成授权。后续接真时，用户接口按本人过滤，机主接口按 `OWNER_USER_ID` 过滤，配送接口按准入状态、服务范围、任务版本和 `courierId` 过滤。页面参数、入口显隐和消息对象均不得扩大 Service 数据范围。

## 契约与 Mock

- 初始化后以 `miniapp/src/api/<domain>.ts` 维护页面可执行契约，先定义类型和稳定函数签名，再实现页面。
- ID 使用 `string`；金额使用整数分；水量使用整数毫升；业务时间沿用 `yyyyMMddHHmmss`。
- 真实接口统一 POST + JSON，成功码为 `0`。Demo Mock 不得倒逼后端接受临时 GET、查询参数或宽泛对象。
- Mock 数据必须固定、可复现，并与 PC 后台共用订单号、设备号、配送任务号和状态口径。
- 页面必须清楚表达模拟边界。Mock 可以在前端内存中推进页面状态，但不得伪造真实扣款、退款、分账、设备执行、微信消息或服务端授权成功。
- 禁止在后端加入小程序测试账号直通、万能验证码、固定 token 或鉴权绕过。

## Wot UI 使用规则

- 优先使用 Wot UI 完成基础组件、表单、反馈、导航和状态展示，不重复封装等价基础组件。
- 全局主题通过 Wot UI ConfigProvider 和主题变量统一管理；具体实现前读取 `config-provider.md` 与 `custom-theme.md`。
- 表单校验、上传、弹层、Toast、Tabbar 等组件必须读取各自参考文档后实现。
- 业务组件可以封装，但不得隐藏资金、设备、身份或履约状态的关键边界。

## D4 验收

小程序初始化后，必须把唯一安装、开发、类型检查、格式检查和构建命令写入项目入口文档。最终 D4 至少验证：

- 微信开发者工具可以实际编译并进入首页；H5 预览不能替代小程序验收。
- 用水、配送和经营能力入口及返回栈正确；多能力可同时存在，能力撤销后入口和页面动作立即失效，数据范围不串线。
- 主流程、异常流程、授权拒绝、加载、空数据、失败和防重复提交均可复现。
- 扫码、定位、上传、订阅消息等微信能力未接真时使用明确的契约状态，不伪造平台成功结果。
- 类型检查、格式检查和生产构建通过，状态同步到 `docs/demo-module-status.md`。

页面和业务链状态分别记录：页面实现情况写入 `docs/demo-module-status.md`，跨端链路状态写入业务链矩阵。模拟环境完成、外部接口接入和生产验收使用独立状态，不相互替代。
