### V-02　主题（Topic）命名规则

我们的现值：

| 方向 | 主题 | 说明 |
|---|---|---|
| 上行 | `up/{deviceNo}/{type}` | type 共 6 个取值，见下表 |
| 下行 | `down/{deviceNo}/cmd` | **下行只有这一个主题**，具体指令类型放在报文体的 cmdType 字段 |

上行 type 的 6 个取值（**这就是全集，平台只收这 6 个，其他的直接丢弃**）：

| type | 含义 | 详见 |
|---|---|---|
| `heartbeat` | 心跳，判在线的依据 | V-03 |
| `status` | 运行状态与故障上报 | V-03 |
| `telemetry` | 遥测（TDS / 水温 / 滤芯 / 信号） | V-03 |
| `ack` | 指令接受回执 | **V-04** |
| `result` | 指令执行结果（含实际出水量） | **V-04** |
| `replay` | 断网补传，载荷是原 status/ack/result 报文并带原 msgId | **V-05** |

⚠ `ack` 和 `replay` 千万别漏：缺 `ack`，每条出水指令都会被判失败（V-04）；
缺 `replay`，断网期间的数据就永久丢了（V-05）。

请确认设备能不能按这套订阅/发布；如果你们已有固定的主题规则，直接给出来，并说明 type 有哪些取值。

### V-03　报文格式与字段定义

请给各类报文的字段定义和样例（JSON 或二进制格式说明都行）：

| 报文类型 | 要说清楚的 |
|---|---|
| 心跳 | 有哪些字段；多久报一次；建议多久没心跳算离线 |
| 遥测 | 支持哪些字段（TDS / 水温 / 滤芯寿命 / 信号强度）；单位和精度；不支持的字段怎么表达 |
| 状态变更 | 状态有哪些取值（在线/离线/运行中/故障/维护…）；是不是主动上报 |
| **时间格式** | 我们的现值：报文里的时间一律 `yyyyMMddHHmmss` 东八区字符串。你们如果用 Unix 时间戳或 UTC，一定注明——这项对不上，所有上行报文都解析不了 |
| **协议版本** | 报文带不带版本号字段？设备分批生产、固件迭代后，新旧协议怎么共存？ |

> 我们目前展示的遥测字段是 TDS、原水 TDS、水温、信号强度、滤芯寿命。设备不支持哪项就注明哪项——页面现在会直接显示这些数值。

### V-04　出水指令与执行回执

取水链路的核心，要定义完整：

| 环节 | 要说清楚的 |
|---|---|
| 指令下发 | 报文字段；水量、水种、出水口编号怎么表达 |
| ACK（接受回执） | **`ackCode` 必填**：只有 `ackCode` = `accepted`（不分大小写）才算受理；**留空、缺字段、或任何其他值（包括 `busy`）都判拒绝，指令直接置失败**。⚠ 固件务必显式回 `accepted`——不回 ackCode 的写法会让每条出水指令都被判失败。如果你们有"忙碌可重试"的语义，把取值告诉我们，我们加重试分支 |
| result（执行结果） | 实际出水量的字段名、单位、精度；成功和失败怎么表达 |
| 部分完成 | 下单 10L 实出 4.98L 这种情况怎么表达 |
| 超时 | 设备没响应时平台该等多久；支不支持指令查询 |
| 并发出水 | 一台设备的多个出水口能不能同时出水？"忙"是设备级还是出水口级？（决定我们扫码预检是按设备拦还是按出水口拦） |

### V-05　断网补传与去重

我们的现值：补传接收已经做好，按报文的 msgId 去重。

| 项 | 待确认 |
|---|---|
| 设备离线期间数据会不会本地缓存并补发 | 是 / 否 |
| **补传时用不用原来的 msgId** | **用（我们的去重直接生效）／ 不用（会重复入账、重复告警，我们得另想去重键）** |
| 缓存容量和存满后的处理 | 能存 ____ 条 / ____ 小时；存满后是丢最早的还是不再记 |

### V-06　设备水种能力与出水口映射

我们目前是按「**一个出水口固定供一种水**」建模的：用户下单时选的水种和出水口绑定的水种
对不上，直接拒单。如果你们的设备实际是「一路出水口能切多种水」，这个模型就得重做，
扫码动线、水种选择页、出水指令格式都会跟着变。

| 项 | 待确认 |
|---|---|
| 单台设备的物理出水口数量 | 标配 ____ 个，可选 ____ 个 |
| 每个出水口是不是固定一种水 | A 固定一口一种水（给个典型配置，比如 4 口 = 纯净水/矿物质水/…）／B 一口可切换多种水（怎么切：指令参数 / 设备屏 / 现场配置）／C 其他 |
| 单台设备最多供几种水 | |
| 水种在出水指令里怎么表达 | 编号 / 名称 / 出水口隐含（不用下发） |
| 设备能力能不能上报 | 平台能不能通过报文查到"这台机器支持哪些水种、有哪些出水口"，还是只能人工建档 |

### V-07　平台之外的出水怎么上报

我们目前只收带指令号（cmdNo）的出水结果——也就是只有平台下单触发的出水才进系统。
如果设备支持本地取水又报不上来，这部分水量就永远不进统计，机主收益会少算，日对账平不了。

| 项 | 待确认 |
|---|---|
| 有没有脱离平台的本地出水 | 投币/纸币：是/否　面板按键直接取水：是/否　管理员或维保放水：是/否　刷实体卡本地放行：是/否 |
| 自检、冲洗、排空会不会真出水 | 是/否；典型每次 ____ mL，频次 ____ |
| 这些出水能不能报给平台 | 能（报文类型和字段：__________）／不能 |
| 如果报不了 | 累计流量能不能按周期报上来让平台对差？字段和频率：__________ |

## 六、P1 设备控制与实体卡

### V-12　远程控制指令集

我们已定义的指令类型（cmdType，放在 `down/{deviceNo}/cmd` 报文体里）：

| cmdType | 指令 | 用途 |
|---:|---|---|
| 1 | 开始出水 | 用户下单后下发，见 V-04 |
| 2 | 停止出水 | 立即中止正在进行的出水（就是"紧急停止"，报文会锚定服务端确认的活动出水订单） |
| 3 | 查询状态 | 运维主动拉设备状态 |
| 4 | 锁机 | 停用设备，拒绝所有出水 |
| 5 | 解锁 | 恢复设备可用 |
| 6 | 参数同步 | 下发配置参数 |
| 7 | 重启 | 远程重启设备 |
| 8 | 价格同步 | 平台改价后推给设备 |

> **2026-08-04 勘误（重要，如果你们照过旧版实现请务必重对一遍）**：旧版表在位置 2
> 漏了"停止出水"，导致 cmdType 2～7 整体错位一格。上表是更正后的**权威**映射，
> 和平台实际下发完全一致。照旧表实现的后果：我们发"停止出水(2)"你们执行查询状态
> （**紧急停止失效**）、我们发"参数同步(6)"你们执行重启。

请确认设备实际支持哪些（不支持的直接标注），并给出各自的报文字段和你们的类型编号。

补充确认：
- V-12.1　价格同步：设备本地存不存价格？平台改价后怎么同步？
- V-12.2　紧急停止：停了之后怎么恢复？要不要现场操作？
- V-12.3　参数同步(cmdType=6)的**参数键集**：请把设备支持配置的每个参数列出来，
  逐项写「键名、数据类型、单位、取值范围、默认值、要不要重启生效、能不能回读」。
  **两点和固件设计直接相关**：①在收到你们的清单之前，平台不会预过滤参数键——
  **固件对不认识的键要防御性忽略，并在 result 里回报**，不要假设平台已经过滤；
  ②我们的 payload 是扁平 JSON 对象（键名 `^[A-Za-z][A-Za-z0-9_]{0,31}$`、值只有
  字符串/数字/布尔、不嵌套不带 null、键数 ≤32、字符串值 ≤64 字符），
  你们的参数形态和这个冲突的话请指出。
- V-12.4　**result 报文的 `partial` 字段**：我们用 `partial=true` 表示「部分生效」
  （指令落「部分完成」而不是「成功」，也不回写参数快照）。请确认三点：这个字段
  存不存在？是不是 JSON boolean（还是字符串 `"true"`/数字 `1`）？部分完成时会不会
  同时说明「哪些子项成功」？类型确认后我们会收紧解析（不是约定类型就拒收该 result 并留痕）。
