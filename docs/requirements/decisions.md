# 需求决策记录

本文件记录当前仍有效并影响后续实施的产品和技术决策。需求状态以 `demo-business-chain-matrix.md` 为准，接口和数据细节以对应契约为准。

## 1. 产品结构

| 编号 | 决策 | 影响范围 |
|---|---|---|
| D-001 | PC 一期采用运营总览、水站、设备、水种套餐、用户、订单中心的 5+1 结构；系统管理保留为基础模块 | REQ-018～REQ-024、REQ-055 |
| D-002 | 主业务菜单一级直达，同一业务域使用页内导航，详情页使用隐藏路由；不保留顶部历史页签和快速入口 | PC 导航与路由 |
| D-003 | PC 负责配置、查询、准入、监控、追溯、裁决和审计，不在后台模拟用户扫码、配送履约或设备执行 | PC 与各业务端职责边界 |
| D-004 | 运营总览保持最小只读范围，完整经营大屏和告警中心在对应业务链实施 | REQ-050、REQ-067 |
| D-005 | 8 种水最终定义、机组层级、设备协议、故障码、微信商户和分账规则属于外部确认项 | 一期外部依赖 |

## 3. 水卡与充值

| 编号 | 决策 | 影响范围 |
|---|---|---|
| D-201 | 数据模型允许一个用户拥有多张卡；一期自助首次购卡仅允许当前没有有效水卡的用户进入 | REQ-006、REQ-007 |
| D-202 | 待支付购卡订单不提前建卡；支付事实确认后，在同一事务内完成发卡、入账、流水和订单回填 | 首次购卡事务 |
| D-203 | 首次发卡使用 `ISSUE_ORDER_ID` 唯一锚点；同一订单不能创建第二张卡 | 发卡幂等 |
| D-204 | 套餐 `expireDays` 决定永久或有限；有限新卡有效期从支付成功时间起算，永久卡有效期为 `NULL`。【2026-07-25 修订】有限期机制仅用于活动赠卡模板，正规付费套餐一律 `NULL`（见 D-213） | 水卡有效期 |
| D-205 | 有限卡充值按 `max(currentExpireTime, paySuccessTime) + expireDays` 续期；永久卡保持永久。【2026-07-25 修订】赠卡不可充值（D-213）后本条转为机制保留：公式由真实 MySQL 事务测试钉住，线上无可达路径 | 已有卡充值 |
| D-206 | 套餐范围必须合法；新卡继承下单时的套餐范围快照，已有卡充值要求套餐范围与卡范围一致 | REQ-074、REQ-075 |
| D-207 | 家庭成员通过显式授权使用卡，支持状态、有效期和单日限额；实际使用人和持卡人分别记录 | REQ-009、REQ-057 |
| D-208 | 客户端 `requestId` 使用 UUID；同一用户和请求生成稳定订单，同请求改卡或改套餐时拒绝 | 订单幂等 |
| D-209 | 支付状态主链为待支付 `1` → 已支付待入账 `2` → 完成 `4`；关闭为 `5`，人工处理为 `6`，退款完成为 `7` | 充值状态机 |
| D-210 | 支付窗口为 30 分钟；付款资格由创建时冻结的卡状态、有效期和 `PAY_EXPIRE_TIME` 判断 | 支付资格 |
| D-211 | Pay-Sim 只用于开发和验收环境，生产环境不注册相关入口 | 内部支付模拟 |
| D-212 | 原始支付报文只用于核验、重放和审计，普通页面不展示 openid、签名或完整交易材料 | 支付数据保护 |
| D-213 | 正规渠道付费购买的水卡一律永久有效（余额与水量不过期，预付卡合规底线）；`EXPIRE_DAYS`/`EXPIRE_TIME` 机制仅用于活动赠卡；赠卡不可充值（usable-list `canRecharge=false` + 创单拒绝「活动赠卡不支持充值」）；充值赠送金额并入主卡、不设独立期限；赠卡发放入口一期未建（2026-07-25 用户拍板） | 付费权益口径 |
| D-214 | 配送订单支付方式二选一：`payWay=2` 全余额（水费+配送费均扣余额，语义不变）；`payWay=3` 混合结算（水费按容器水量抵扣 `BALANCE_ML`，配送费为服务费仍扣余额，两步同事务、任一失败整体回滚）。水量换算表单一出处 `DeliveryPricing`（3L袋=3000ml、5L桶=5000、10L桶=10000、20L桶=20000，前端同表同步）；金额口径修订（E2E-03 规则2）：`ORDER_AMOUNT`=(payWay=2?水费:0)+配送费，任务行 `WATER_AMOUNT` 同口径，快照新增 payWay/waterMl/priceWaterAmountFen（价目参考）；旧包无 payWay 按 2 兼容，同 requestId 改 payWay 拒绝；自动补货暂仅支持余额（规则表无支付方式列，fail-closed）；赠卡消费不受限（仅充值受 D-213 限制）；补偿边界：payWay=3 单以水量回补为主，待 E2E-04（2026-07-25 用户拍板） | 配送支付口径、REQ-011、REQ-073 |
| D-215 | 后台申诉列表按案件维度（`ws_delivery_appeal.TASK_ID`）聚合分页：一行 = 一个配送任务，同订单多次申诉不再多行。聚合行展示值取代表申诉=活跃申诉（`APPEAL_STATUS=1`，由 `uk_appeal_active_task` 保证至多一条），无活跃则取最近一条（`CREATE_TIME DESC, ID DESC`），故行内 `appealStatus` 即案件当前状态；附带 `appealCount`/`activeAppealId`/`firstAppealTime`/`lastAppealTime`，排序为待处理案件优先、其余按最近申诉时间倒序。状态筛选作用于当前状态，历史上出现过该状态不参与命中（同一案件在多筛选下重复出现更难判读）；`orderNo` 模糊匹配不变。聚合必须在 SQL 层完成（前端聚合会被分页边界切断案件），分页 total 为案件数。数据层零改动：申诉表结构不动、历史行完整保留、裁决仍按单条 `appealId` 走包A 事务。证据详情新增 `appealHistory`（同任务全部申诉正序，含裁决结果、裁决人、裁决时间），共键核验 `linkStatus=mismatch` 时同样不下发；历史条目只出文本与裁决结论，媒体元数据仍只针对当前 `appealId`（2026-07-25 用户拍板） | REQ-017、PC 申诉处理页、E2E-03 包C |

## 6. 安全与实施边界

1. 余额、水量和权益变更使用数据库原子更新并记录唯一业务流水。
2. 支付通知、退款通知和设备消息使用数据库唯一键保证幂等。
3. 设备控制必须经过 `ws_command` 状态机，不允许页面绕过服务端直接控制设备。
4. 机主和配送员数据范围由 Service 层按登录主体强制过滤。
5. 正式微信、物理设备、对象存储和生产基础设施分别完成接入和验收，不以模拟结果替代。
