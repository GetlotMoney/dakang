# H3 取水异常退差契约（独立草案）

> 状态：待产品评审，尚未进入实现  
> 拆分日期：2026-07-21  
> 历史来源：2026-07-21 早期 L2/H3 混合草案中的 H3 章节；原混合草案因已作废且曾造成误引用，已从交付源码删除  
> 实施边界：状态机、结算算法和权限确认前，不实施 H3 写接口、数据库迁移或资金补偿。

本文定义取水异常退差的评审范围，供 E2E-04 售后退款与补偿链设计使用。状态机、金额算法、权限和数据迁移需在实施前确认。

## 1. 目标与范围

H3 讨论 PC 运营人员对取水订单异常终态的处理：平台根据服务端权威订单、设备结果和水卡账本，计算应结算量与应退差额，形成订单、卡、流水和审计的一致终态。

拟议范围仅包含：

- `ORDER_TYPE=1` 的扫码取水订单；
- `ORDER_STATUS=6` 的异常待处理订单；
- `PAY_WAY=2` 水卡余额或 `PAY_WAY=3` 水卡水量；
- 服务端派生处理结果，PC 只提交处理说明；
- 卡权益补偿与 `FLOW_TYPE=4` 补偿流水。

明确不包含：

- L2 购卡充值、Pay-Sim 或微信支付事实处理；
- `PAY_WAY=1` 微信支付的真实退款；
- 配送订单、配送申诉或人工任意指定补偿金额；
- 用 PC Mock 操作冒充真实退款、余额入账或设备结果；
- 因本次文档拆分而恢复当前已禁用的异常处理按钮。

## 2. 当前仓库事实

- PC 订单中心的异常处理真实写入口当前未实现，页面按钮保持禁用。
- `ws_order`、`ws_card`、`ws_wallet_flow` 已存在；历史提案计划复用水卡补偿原子方法。
- 当前订单追溯已经对订单、指令、设备、出水口、状态、时间和水量证据执行 fail-closed 校验；这些只读证据不等于 H3 写链已经具备实施条件。
- `ORDER_STATUS=6` 在取水订单中表示异常待处理；该文案不得复用于 L2 充值订单的支付后权益异常。

## 3. 历史提案的接口形态（未冻结）

历史 v1.5 提议：

```text
POST /order/order/handle-exception
```

拟议鉴权：

- 管理端登录；
- 独立权限 `order:order:handleException`；
- Controller、菜单功能点和 Service 权限三方一致；
- 写操作日志与资金级审计。

拟议请求：

```text
orderId: 十进制 string，必填
handleRemark: string，必填，最长 500
```

请求不得包含可由前端决定的退款金额、补偿水量、目标状态或处理算法。所有金额、水量和终态必须由服务端权威数据派生。

## 4. 历史提案的前置栅栏（待终审）

在任何状态或账务写入前，拟议至少校验：

1. 订单存在且未逻辑删除。
2. `ORDER_TYPE=1` 且当前 `ORDER_STATUS=6`。
3. `PLAN_ML` 为正整数，`ACTUAL_ML` 为整数且满足 `0 <= ACTUAL_ML < PLAN_ML`。
4. 订单关联的卡存在，卡 `USER_ID` 与订单 `USER_ID` 一致。
5. 支付通道仅为水卡余额或水卡水量；微信支付订单明确拒绝自动处理。
6. 订单、指令、设备、出水口与结果水量的追溯共键均通过；只读追溯已经是 mismatch 的订单不得进入补偿。
7. 计划水量、实际水量、订单金额、单价快照及其整数值域、上限和溢出检查全部通过。
8. 已存在的补偿流水、删除态流水、重复流水或账本 AFTER 断裂均转人工，不得继续自动补偿。

任一校验不通过时，订单、卡、流水和持久业务状态必须零变化。

## 5. 历史派生算法提案（待重新确认）

历史 v1.5 提议：

- `actualMl == 0`：候选目标状态为 7；
- `0 < actualMl < planMl`：候选目标状态为 4；
- 结算水量：`min(actualMl, planMl)`；
- 水卡余额通道候选退差：`max(0, orderAmount - ceil(结算水量 × unitPriceFenPerLiter / 1000))` 分；
- 水卡水量通道候选退差：`planMl - 结算水量` 毫升。

以上算法不得因从 v1.5 抽出而视为已确认。H3 终审必须重新核对：

1. 状态 7 对水卡权益返还的业务语义是否准确。
2. `orderAmount`、`PACKAGE_SNAP.unitPriceFenPerLiter` 与实际扣减流水谁是权威来源。
3. 单价快照缺失、非法或不一致时是否必须 fail-closed；未经产品确认和技术评审，不得沿用“按单价 0 全额退”的历史兼容行为。
4. 已发生部分结算时订单状态 4、完成时间和补偿流水的组合是否符合 PC 与小程序文案。
5. 余额退差和水量退差的最大值、最小值及 Long 溢出边界。
6. 当前结算函数是否可以安全复用，或应抽取新的唯一权威函数；禁止复制出第二套金额公式。

## 6. 事务与并发提案（待终审）

历史方案拟采用单一受控事务：

1. 对订单执行条件状态 claim，仅允许一个请求从状态 6 取得处理权。
2. 按固定顺序锁定订单和卡，读取包含逻辑删除态在内的资金流水。
3. 拒绝任何既有、重复、错卡、错用户、错通道或断裂的补偿流水。
4. 使用原子 `UPDATE ... SET balance = balance + delta` 修改对应余额或水量，并校验影响行数精确为 1。
5. 插入一条带 `AMOUNT_CHANGE/ML_CHANGE` 及双维 `AFTER` 的 `FLOW_TYPE=4` 流水。
6. 更新订单精确终态、`FINISH_TIME` 与服务端生成的处理摘要。
7. 订单、卡、流水和成功审计共同提交；任一步失败整体回滚，使订单仍可安全复核。

重复请求不得仅凭订单已是 4 或 7 就返回成功。必须同时核对精确目标状态、恰好一条有效补偿流水、卡/用户/通道/变动值、完整 AFTER 连续性及卡终值。任一不一致均为 mismatch，并进入人工处理。

下列内容尚未冻结，须在 H3 独立终审中决定：

- claim 与锁顺序及死锁重试策略；
- H3 补偿流水的稳定业务幂等键和唯一约束；
- 失败审计如何在主事务回滚后可靠保存；
- 人工对账入口及恢复后的合法状态迁移；
- 已退款、部分退款及既有补偿污染的迁移处理。

## 7. PC 页面提案（待终审）

H3 若后续获准实施，PC 可以复用当前订单追溯抽屉和异常订单列表，不新增一级菜单。候选交互为：

- 只对通过后端资格预检的 type-1/status-6 订单显示真实处理入口；
- 页面展示服务端派生的计划量、实际量、结算量、候选退差和数据来源；
- 操作人只能填写处理说明，不能编辑金额、水量、支付通道或目标状态；
- 提交前二次确认并防重复提交；
- 返回后重新读取真实订单追溯、卡余额、补偿流水与审计结果；
- 任何关联不一致显示 mismatch，不拼成“补偿成功”。

在后端合同、权限、迁移和对抗测试通过独立终审前，当前禁用按钮不得恢复，前端 Mock `fetchResolveWaterException` 不得替换为真实资金写接口。

## 8. 独立终审最低测试清单

后续 H3 终审至少要求常驻覆盖：

1. 非取水订单、非状态 6、微信支付订单全部拒绝且零副作用。
2. 计划量、实际量为空、非整数、负数、越界或溢出全部拒绝。
3. 订单—指令—设备—出水口—实际水量任一共键错位拒绝。
4. 卡不存在、卡归属错、逻辑删除卡及通道错位拒绝。
5. 单价快照缺失、非法、被篡改或与账本不一致时 fail-closed。
6. 余额通道、水量通道及零出水/部分出水的派生结果精确。
7. 两个及以上并发请求只能一个事务完成，不重复补偿。
8. claim 失败后只有精确终态与完整唯一流水一致时才允许幂等成功。
9. 已有一条污染流水、重复流水、删除态流水或错通道流水全部转人工。
10. 每一笔流水双维 AFTER 与前后流水连续，卡终值等于最后 AFTER。
11. 卡更新、流水插入、订单更新或审计任一步失败时主事务整体回滚。
12. 失败证据在主事务回滚后仍可按已确认方式查询。
13. PC 不允许篡改服务端派生的金额、水量和目标状态。
14. Long 身份 ID 从后端到 PC 全程保持 string。

## 9. 重新打开实施的条件

H3 只有同时满足以下条件后，才可以从“独立草案”进入实现：

1. 用户明确要求对 H3 单独终审。
2. 状态语义、结算算法、权威数据源、唯一键、并发顺序和失败审计全部冻结。
3. SQL 迁移方案只在独立临时 MySQL 验证通过。
4. 后端和 PC 任务取得独立实施授权。
5. 涉及主库迁移或持久余额/水量变化时，再取得当次明确授权。
