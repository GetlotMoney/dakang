# 六维达康项目综合分析

- 文档版本：`DOC-PROJECT-ANALYSIS-V1`
- 日期：2026-07-25
- 分析性质：只读代码、需求、运行配置与现有证据审查
- 审核强度：两轮。原因是结论同时影响源码交付、资金、设备指令和后续上线判断；第二轮使用独立 Agent 分别复核后端、前端/运行时和需求证据。

## 一、结论

项目不是空壳，已经具备较成熟的 PC 管理后台、小程序页面基座，以及扫码取水、水卡生命周期、配送三条模拟业务链。需求追踪、幂等设计、资金流水、设备消息去重和 Mock/Real 边界也有较扎实的基础。

但当前收到的源码交付包不能作为可重建版本，也不能据此上线：

1. 当前包缺少整个 `server/src/main/java/com/jbk/tool/data/`，现有后端有 700 多处 import 依赖该目录，静态上已经可以确定无法编译。
2. 普通小程序开发环境会把多个业务域切到真实接口，并通过测试手机号换取真实会话；连得上后端时，普通开发操作可能改变余额、订单或配送状态。
3. 设备指令存在“先发 MQTT、后写已发送状态”的时间差，快速 ACK/result 与超时并发时，命令状态和订单结算可能分裂。
4. 员工密码仍采用可逆加密，私钥又随源码交付；固定 JWT、数据库、Redis、MQTT 凭据也不适合共享网络或生产。
5. 当前部署脚本只运行一个后端测试类，已有数据库不会自动执行版本迁移，当前源码的 GUI 与完整验收证据也没有重新闭合。

因此，当前最合理的路线是：暂停在这份源码包上继续做真实业务实现，先从原始仓库恢复完整源码并修复打包规则，同时收紧测试登录和默认运行方式；随后修复设备状态竞态并跑完整验证。E2E-04 售后退款与补偿可以并行停留在业务故事、接口契约和页面 Mock 阶段，但在验收门打开前不能执行真实资金写入。

## 二、项目现状

### 2.1 产品与技术结构

- PC 公司后台：Vue 3、Element Plus、TypeScript、Vite，采用 5+1 业务结构。
- 后端：Java 17、Spring Boot 3.5.11、MyBatis-Plus、Sa-Token。
- 微信小程序：uni-app、Vue 3、TypeScript、Wot UI。
- 设备接入：EMQX 5.8、MQTT QoS 1。
- 数据层：MySQL 8、Redis 7。
- 本地交付：MySQL、Redis、EMQX、后端、Web 五容器。

代码和页面并不稀薄：PC 24 个路由组件均有对应页面，小程序 28 个路由均有对应页面；水站、设备、用户、水卡、订单和配送等模块已有较多真实接口实现。

### 2.2 需求与业务链成熟度

- 总需求：110 条。
- 当前 MVP/骨架范围：55 条，其中 48 条产品需求、7 条工程治理需求。
- B01～B24：6 条整链闭环候选、15 条部分完成、3 条仅有契约。
- E2E-01～03：完成模拟环境内部闭环并验收模拟范围。
- E2E-04～08：尚未开工或尚未形成完整链路。
- 8 条 E2E 的正式外部能力均未闭合。

这里的“模拟环境验收”只证明固定 Mock、Pay-Sim 或协议模拟器里的内部路径，不等于正式微信、真实支付、物理设备和生产网络已经上线。

## 三、关键问题

### 3.1 必须先修：当前源码包不完整

事实：

- `server/src/main/java/com/jbk/tool/data/` 不存在。
- 后端仍有 700 多处 `com.jbk.tool.data.*` 引用，涉及 160 多个类型。
- `tools/package-source.sh` 使用未限定层级的 `--exclude='data/'`，会把根目录运行数据和嵌套的 Java `tool/data/` 一起排除。
- 打包后的检查只确认文档和少量规定文件存在，没有在解压后的新目录执行后端编译。

判断：

根因高度指向打包排除规则。原始仓库可能仍然完整，但当前交付包本身已经不能编译，不能靠猜测重建 160 多个数据对象。

处理要求：

1. 回到原始仓库确认 `server/src/main/java/com/jbk/tool/data/` 完整存在。
2. 将排除规则限定为项目根目录下的运行数据目录。
3. 在打包后增加代表性 Po/Bo/Vo 文件存在性检查。
4. 解压到全新目录，执行完整后端测试或至少完整打包；只有这个“重新解压后也能构建”的包才可交付。

### 3.2 必须先修：测试登录和默认开发方式会越过安全边界

事实：

- `/mini/test-login/by-phone` 可根据现有手机号直接签发会话，没有密码、验证码或已有登录态。
- 该入口跟随 Pay-Sim 开关，主 Docker Compose 默认打开 Pay-Sim。
- `miniapp/env/.env.development` 将 device、order、card、recharge、delivery 设置为 `real`，同时写入测试手机号和固定局域网后端地址。

影响：

普通 `dev:h5` 或 `dev:mp-weixin` 并非安全的全 Mock 环境。只要后端可达，页面点击就可能形成真实数据库动作；后端端口若暴露到共享网络，知道手机号的人还可能冒充用户。

处理要求：

- 标准开发和交付命令默认全 Mock。
- 真实域只允许通过名称明确的受控验收命令开启，并显示当前连接目标和会产生的副作用。
- 删除公网可调用的手机号直通 HTTP 入口；测试需要会话时，改用隔离测试夹具或一次性测试凭据。
- Pay-Sim 与测试登录使用独立开关，且默认关闭。

### 3.3 必须先修：设备指令状态与订单结算可能分裂

事实：

- `WsCommandServiceImpl.doSend` 先发布 MQTT，再把命令从 PENDING 更新为 SENT。
- 快速 ACK 若在状态更新前到达，`onAck` 会因为命令仍是 PENDING 而忽略它。
- result 或超时并发时，即使状态条件更新失败，现有路径仍可能继续推动订单结算。
- 已终态结果重试未完整核对新结果是否与首次保存的 payload、实际出水量一致。

影响：

可能出现“命令仍显示待发送、失败或超时，但订单已经完成或退款”的矛盾状态。

处理要求：

- 先把待发送事实可靠写入数据库，再由后台可靠发送；这通常叫 outbox，直白说就是“先记账，再发消息”。
- 只有命令终态真正更新成功，或重放结果与第一次保存的终态事实完全一致时，才允许结算。
- 增加早到 ACK、超时与 result 并发、冲突实际出水量、结算中途崩溃恢复测试。

### 3.4 上线前必须完成：密码、密钥和网络隔离

事实：

- 员工密码使用随源码携带私钥的可逆加密。
- JWT、数据库、Redis、MQTT 等存在固定凭据。
- MySQL、Redis、MQTT、EMQX 管理台、后台和 API 默认发布到宿主机所有网卡。
- 仓库中没有看到完整的 MQTT 客户端认证与主题 ACL 配置。

处理要求：

- 员工密码迁移为单向哈希，初始密码随机生成并强制首次修改。
- 所有固定凭据改为环境或 Secret 注入，部署前轮换。
- 本地 Demo 默认只绑定 `127.0.0.1`。
- 正式设备按设备身份限制可发布和订阅的 MQTT 主题。

### 3.5 第二批修复：发布、数据库和数据契约

- `deploy/build-all.sh` 只运行 `MiniAuthServiceTest`，未把 63 个后端测试文件纳入发布门。
- MySQL 初始化脚本只对空数据卷生效，已有环境不会自动运行 `deploy/mysql/migrations/`。
- 设备和出水口删除尚未完整检查历史订单、指令、消息和告警引用；已有历史记录时应只允许停用。
- PC 的水站、设备、用户、水卡等接口仍把部分 Java Long ID 写成 JavaScript `number`，大 ID 可能出现末位变化。
- `server/sql/ws_user_card.sql` 与正式初始化脚本已有字段和唯一索引漂移。

## 六、三种推进路线

### 路线 A：只修复源码包后继续做功能

优点是最快恢复开发；缺点是测试登录、真实开发默认值和设备竞态仍会把风险带入新功能。不能作为推荐路线。

### 路线 B：先恢复可重建版本，再处理三个高风险点，然后继续业务链

顺序：

1. 恢复 `tool/data`，修复打包脚本，并验证重新解压后的源码。
2. 关闭手机号直通和普通开发的真实写入默认值。
3. 修复设备指令、ACK/result 与订单结算竞态。
4. 跑完整后端、PC、小程序、容器和 8081 GUI 验证。
5. 再进入 E2E-04 的真实实现；契约和页面 Mock 可与前四步并行。

这是推荐路线，既处理了会导致返工或资金错误的问题，也不会无期限冻结产品确认。

### 路线 C：等所有微信、支付和样机资料齐全后再继续

最保守，但会把可独立完成的源码、契约和内部质量工作也一起停住，当前没有必要全面冻结。

## 七、推荐执行清单
